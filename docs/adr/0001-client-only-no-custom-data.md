# v1 是纯客户端模组：不引入自定义数据与网络同步

我们原本计划引入附属自己的"扩展元数据"（分类文件夹、手写优缺点、单位覆盖、背景资料），并由自建网络通道同步到客户端。事实核查后放弃了这一层：TACZ 的每个属性修改器都提供 `getPropertyDiagramsData(gunItem, gunData, cacheProperty)`，其 `DiagramsData` 已包含**基准占比、修改量、好坏方向（`positivelyBetter`）与本地化文案**，且纯客户端可调用；分类也可直接复用 `AttachmentType`。（当时以为 TACZ 的标签体系是第二条退路，1.1.8 实测已否掉：tag 是"枪↔配件"的兼容关系索引，覆盖不完整、不互斥、命名不系统，当不了分类，见 `docs/research/tacz-attachment-tags.md`。）因此 v1 决定**不引入任何附属自定义数据、不自建网络通道、不要求服务端安装**，全部功能为客户端行为，数据源限于 TACZ 已同步的 common 数据与 ItemStack NBT。

## Consequences

- 模组可加入任何已装 TACZ 的服务器（含陌生服务器），无需服务端配合，也不存在"服务端版本不一致"的同步问题。
- 无法为个别配件定制分类文件夹、手写优缺点、单位覆盖与背景资料；描述文案只能沿用 TACZ 原生 tooltip key。
- **这不是"还没做"，而是"不该做"。** 起初把这一层记成"v1.1 的入口，届时才需要引入同步通道"，后来明确否掉了：**配件怎么分类、怎么介绍，是枪包作者的领域**，本模组不替作者定义内容，也不为它另立一套平行体系。分类只用 `AttachmentType`，文案交给作者。所以 v1.1 也不会为此引入数据层或通道。（决策与理由见 issue #3 的解决评论。）
- 属性文案的单位与舍入由 TACZ 决定（单位只存在于其拼好的字符串里，字段中不携带），本项目无法改写。
